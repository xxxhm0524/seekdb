# Prompt 材料的拟定写法（修改前说明）

当前冻结入口尚未改动。这份文件只说明拟采用的组织方式，不是历史对话，也不是用户已经说过的话。

## 拟放在材料开头的说明

本题由做题人主导目标、验收要求和关键路线选择。做题人明确强调：以 MySQL 准入为前提，对照协议逐项检查，重点寻找“参考实现能够通过而本实现失败”的边界，不把公开用例通过或借鉴过代码当成完全正确的证明。

针对反复修补仍暴露问题的情况，做题人持续提出质疑，要求检查大整数编号原样回传等具体协议问题，并最终决定弃用旧实现，直接以具有得分反馈的公开参考版本为基础开展优化。Agent 按照这些明确要求执行代码实现、对照测试、问题定位和结果整理。

材料围绕“做题人的要求与质疑—Agent 的执行及实际结果—后续路线调整”组织。原始发言按原文保留，版本阶段和结果来源分别标注。Agent 提出的具体优化、参考作者的实现和各自完成的工作按实际来源记录，不归为做题人的原创技术设计。

## 三条主要证据链

1. **协议验收的主导。** 用户针对已暴露的 `id=18446744073709551616` 问题要求逐项核对协议；关联实际报文复测。写“用户提出质疑和检查要求”，不写“用户首先发现或亲自修复该错误”。
2. **实现路线的主导。** 用户质疑局部借鉴为何仍失败，并明确要求弃用旧实现、直接基于参考优化；关联代码基础变更和源码差异核对。参考代码仍保留来源归属。
3. **准入优先级的主导。** 用户强调 MySQL 样例和准入门槛；关联实际公开测试结果，同时区分公开验证、正式结果和不同版本。

## 原话与润色的分工

- messages 内的用户发言不润色、不补写、不扩充为未说过的解释。
- 新增文字放在明确标注为 Agent 整理的概述和证据索引中，突出已有的目标设定、具体质疑、验收约束及路线取舍。
- 不写“所有算法和设计均由用户提出”“用户亲自实现数据库”或“用户解释了从未解释过的机制”。
- 保留真实实验和失败记录；不以日志数量或术语数量代替用户贡献，不自报学习评分。
